Week 11: Testing, Debugging & Performance Profiling

1. The Challenge of Embedded Debugging

Debugging embedded firmware is fundamentally different from debugging desktop code: - Your target microcontroller does not have a computer monitor or keyboard attached. - Code interacts with real-time physical voltages, motors, and high-frequency communication signals. - Halting the CPU at the wrong instant can physically damage hardware (e.g., leaving a high-power motor MOSFET energized).

 1. PRINTF-STYLE DEBUGGING (THE HEISENBUG DILEMMA):
 Code: printf("Sensor value: %d\n", val);
 * Consumes 10-50 ms over a 9600 baud serial UART line!
 * Alters real-time execution timing, making timing-dependent bugs vanish during debugging
   (known as a "Heisenbug")!
 * Stalls Interrupt Service Routines (ISRs) and severely inflates Flash code size.

 2. MODERN HARDWARE ON-CHIP DEBUGGING (JTAG / SWD):
 Debug Probe [ST-Link / J-Link] <== SWD (2 Wires) ==> Target Microcontroller [CoreSight]
 * Non-intrusive, zero-overhead hardware breakpoints and watchpoints.
 * Single-step through assembly instructions and inspect internal peripheral registers live!

2. Hardware Debug Interfaces: JTAG vs. SWD

To program Flash memory, control the processor core, and step through code line-by-line, microcontrollers feature hardware debug ports:

 JTAG INTERFACE (IEEE 1149.1 - 4/5 Wires)
 [Debug Probe] --- TDI (Test Data In) ------> [ Chip 1 ] ---> [ Chip 2 ] (Daisy Chain)
               <-- TDO (Test Data Out) <-----+           <---+
               --- TCK (Test Clock) -------->
               --- TMS (Test Mode Select) -->
               --- nTRST (Optional Reset) -->

 SWD INTERFACE (ARM Serial Wire Debug - 2 Wires)
 [Debug Probe] <== SWDIO (Bidirectional Serial Data) ==> [ Single ARM MCU ]
               --- SWCLK (Clock Reference) ------------>

Protocol Comparison

Characteristic JTAG (IEEE 1149.1) SWD (ARM Serial Wire Debug)
Physical Pin Count 4 to 5 pins (TDI, TDO, TCK, TMS, [TRST]) 2 pins (SWCLK, SWDIO) + GND
Data Direction Dedicated unidirectional lines Bidirectional half-duplex packets on SWDIO
Multi-Chip Daisy Chaining Supported (can chain MCU + FPGA on 1 header) Primarily point-to-point
Boundary Scan Supported (tests PCB electrical shorts/opens) Not supported (focused on CPU debugging)
Pin Overhead on MCU High (consumes 5 precious GPIO pins) Minimal (frees pins for peripheral sensors)
Standard Ecosystem Universal (ARM, RISC-V, DSPs, FPGAs) Specialized exclusively for ARM Cortex processors

3. Profiling & Execution Time Measurement

How do you know if your control loop executes in \(150\,\mu\text{s}\) or \(1500\,\mu\text{s}\)? In embedded systems, there are two primary methods to measure execution time:

 METHOD 1: GPIO PIN TOGGLING (Measured on an Oscilloscope or Logic Analyzer)
 GPIOA->BSRR = (1 << 5);      // Drive Test Pin HIGH
 execute_algorithm();         // Function under test
 GPIOA->BSRR = (1 << (5+16)); // Drive Test Pin LOW
 * Width of the physical square pulse equals the exact execution time!

 METHOD 2: ARM CORTEX-M DWT CYCLE COUNTER (Measured in Software)
 DWT->CYCCNT = 0;             // Reset hardware 32-bit cycle counter
 execute_algorithm();
 uint32_t cycles = DWT->CYCCNT; // Exact number of CPU clock cycles elapsed!

4. Static Analysis Tools: Catching Bugs Before Flashing

Static Analysis is the process of inspecting C source code without running it, detecting hidden bugs, undefined behaviors, and safety hazards during compilation.

 +-------------------------------------------------------------------------+

5. Unit Testing for Embedded Systems: Hardware Mocking

Testing embedded C code on physical hardware is slow, expensive, and difficult to automate in Continuous Integration (CI) pipelines.

The industry solution is Unit Testing on the Host PC with Hardware Mocking:

 TRADITIONAL TESTING (Slow & Hardware Dependent):
 Code compiled for ARM ---> Flashed to MCU via USB ---> Manually probed with a multimeter.

 EMBEDDED UNIT TESTING (Fast, Automated & Scalable):
 Sensor Algorithm compiled for PC (x86_64) ---> Run with Unity / CMock Test Framework
 * Hardware registers (I2C, ADC, Timers) are replaced with virtual mock structures in C!

6. Mini-Project 1: ARM DWT Cycle Counter Precision Profiler ⏱️⚡

🎯 Objective

When writing performance-critical signal processing or control loops, developers must know down to the exact clock cycle how long algorithms take to execute. In this project, you will activate the hardware Data Watchpoint and Trace (DWT) unit on the ARM Cortex-M core to benchmark the cycle counts of floating-point arithmetic versus integer bit-manipulation on the STM32 Nucleo-C031C6.

🛠️ Hardware Setup (Wokwi)

  • Target Board: board-st-nucleo-c031c6 (ARM Cortex-M0+)
  • Diagnostic Serial Stream: Direct USB Virtual COM Port at 115200 baud.
  • Benchmark Heartbeat LED: User LED on D13 (PA5).

Pin Wiring Table

Component Pin / Terminal STM32 / Board Pin Electrical Function
Serial Terminal USB VCP Virtual COM Port Telemetry Console (115200 baud, 8-N-1)
Benchmark LED Anode (PA5) D13 Toggled upon every completed test cycle
Common Ground Cathode GND Ground Reference

📝 Problem Statement & Logic Flow

  1. DWT Hardware Initialization:
    • Enable the CoreDebug trace control bit: CoreDebug_DEMCR |= (1UL << 24);.
    • Enable the cycle counter in DWT Control register: DWT_CTRL |= (1UL << 0);.
  2. Benchmark 1 (Floating-Point Division):
    • Reset cycle counter to zero (DWT_CYCCNT = 0).
    • Perform division on two 32-bit floating-point variables (volatile float res = 12345.67f / 3.1415f;).
    • Capture float_cycles = DWT_CYCCNT;.
  3. Benchmark 2 (Integer Bit-Shift Division):
    • Reset DWT_CYCCNT = 0.
    • Perform equivalent integer division by 4 using bit-shifting (volatile uint32_t res = val >> 2;).
    • Capture int_cycles = DWT_CYCCNT;.
  4. Speedup Analysis & Telemetry:
    • Transmit exact cycle counts and speedup ratio over UART: \[\text{Speedup Ratio} = \frac{\text{Float Cycles}}{\text{Integer Cycles}}\]
[PROFILER]: Float Division Execution: 104 cycles
[PROFILER]: Integer Bit-Shift Execution: 1 cycle
[PROFILER]: Performance Speedup Factor: 104x faster!

// ============================================================================
// Mini-Project 1: ARM Cycle Counter Precision Profiler (Nucleo-C031C6)
// ============================================================================

#define CoreDebug_DEMCR (*(volatile uint32_t *)0xE000EDFCUL)
#define DWT_CTRL        (*(volatile uint32_t *)0xE0001000UL)
#define DWT_CYCCNT      (*(volatile uint32_t *)0xE0001004UL)

void initCycleCounter() {
  CoreDebug_DEMCR |= (1UL << 24); // Enable TRCENA bit
  DWT_CTRL        |= (1UL << 0);  // Enable CYCCNTENA bit
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_BUILTIN, OUTPUT);
  initCycleCounter();

  Serial.println("==================================================");
  Serial.println("   ARM Cortex-M Hardware Cycle Profiler Ready     ");
  Serial.println("==================================================");
}

void loop() {
  // Test 1: Software Floating-Point Division
  volatile float f_num = 12345.67f;
  volatile float f_den = 3.1415f;
  
  DWT_CYCCNT = 0; // Reset counter
  volatile float f_res = f_num / f_den;
  uint32_t float_cycles = DWT_CYCCNT;

  // Test 2: Hardware Single-Cycle Integer Bit-Shift Division
  volatile uint32_t i_num = 12345;
  
  DWT_CYCCNT = 0; // Reset counter
  volatile uint32_t i_res = i_num >> 2;
  uint32_t int_cycles = DWT_CYCCNT;

  // Telemetry Output
  digitalWrite(LED_BUILTIN, !digitalRead(LED_BUILTIN));

  Serial.print("[PROFILER]: Float Division Execution:    ");
  Serial.print(float_cycles);
  Serial.println(" cycles");

  Serial.print("[PROFILER]: Integer Bit-Shift Execution: ");
  Serial.print(int_cycles);
  Serial.println(" cycles");

  Serial.print("[PROFILER]: Speedup Factor:               ");
  Serial.print(float_cycles / (int_cycles > 0 ? int_cycles : 1));
  Serial.println("x faster!\n");

  delay(2000);
}
// ============================================================================
// Mini-Project 1: Bare-Metal ARM DWT Profiler Driver
// Target: STM32 Nucleo-C031C6 (ARM Cortex-M0+)
// ============================================================================
#include <stdint.h>

#define COREDEBUG_DEMCR (*(volatile uint32_t *)0xE000EDFCUL)
#define DWT_CTRL        (*(volatile uint32_t *)0xE0001000UL)
#define DWT_CYCCNT      (*(volatile uint32_t *)0xE0001004UL)

void dwt_profiler_init(void) {
    COREDEBUG_DEMCR |= (1UL << 24); // Enable Global Trace (TRCENA)
    DWT_CYCCNT       = 0;           // Reset counter
    DWT_CTRL        |= (1UL << 0);  // Enable Cycle Counter (CYCCNTENA)
}

uint32_t profile_algorithm(void (*func)(void)) {
    DWT_CYCCNT = 0;
    func();
    return DWT_CYCCNT; // Single-cycle precision elapsed instruction cycles
}

7. Mini-Project 2: Embedded Unit Testing Harness with Pass/Fail LEDs 🧪✅

🎯 Objective

In automotive (ISO 26262) and medical device development, untested code is forbidden from deployment. In this project, you will build an automated self-testing firmware harness for the STM32 Nucleo-C031C6 that executes automated unit tests on boot, verifying an ADC-to-Voltage translation function using hardware Pass (Green) and Fail (Red) LED indicators.

🛠️ Hardware Setup (Wokwi)

The circuit connects two diagnostic status LEDs with 220Ω current-limiting resistors: * Pass LED (Green): Connected to pin D12 (PA6). * Fail LED (Red): Connected to pin D11 (PA7). * Common Ground: LED cathodes tied to GND.

Pin Wiring Table

Component Pin / Terminal STM32 / Board Pin Electrical Function
Pass LED (Green) Anode (via 220Ω) D12 (PA6) Test Suite All-Pass Indicator
Fail LED (Red) Anode (via 220Ω) D11 (PA7) Assertion Failure Indicator
Both LEDs Cathodes (\(-\)) Common GND Ground Reference

📝 Problem Statement & Logic Flow

  1. Unit Under Test (UUT): Implement a robust integer math scaling function: uint32_t adcToMillivolts(uint16_t raw_adc); which scales 12-bit ADC raw values (\(0\) to \(4095\)) to millivolts (\(0\) to \(3300\text{ mV}\)). It must clamp out-of-bounds readings (\(> 4095\)) defensively.
  2. Automated Unit Test Suite:
    • Test 1 (Zero Scale): Verify that input 0 yields exactly 0 mV.
    • Test 2 (Full Scale): Verify that input 4095 yields exactly 3300 mV.
    • Test 3 (Mid Scale): Verify that input 2047 yields 1648 mV to 1652 mV (\(\pm 2\text{ mV}\) precision band).
  3. Hardware Test Reporting:
    • If all tests pass: turn Green LED on D12 HIGH, Red LED LOW, and print "[ALL TESTS PASSED]: Green LED illuminated.".
    • If any test fails: turn Red LED on D11 HIGH, Green LED LOW, and print assertion error details.

// ============================================================================
// Mini-Project 2: Embedded Unit Testing Harness (Nucleo-C031C6)
// ============================================================================

#define LED_GREEN 12 // Pass Indicator (PA6)
#define LED_RED   11 // Fail Indicator (PA7)

// Unit Under Test (UUT): Scales 12-bit ADC (0-4095) to Millivolts (0-3300 mV)
uint32_t adcToMillivolts(uint16_t raw_adc) {
  // Defensive clamp against out-of-bounds inputs
  if (raw_adc > 4095) {
    raw_adc = 4095;
  }
  // Fixed-point 32-bit integer arithmetic
  return ((uint32_t)raw_adc * 3300UL) / 4095UL;
}

// Unit Test Cases
bool test_zero_scale() {
  return adcToMillivolts(0) == 0;
}

bool test_full_scale() {
  return adcToMillivolts(4095) == 3300;
}

bool test_mid_scale() {
  uint32_t mv = adcToMillivolts(2047);
  return (mv >= 1648 && mv <= 1652); // Precision tolerance band
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_GREEN, OUTPUT);
  pinMode(LED_RED, OUTPUT);
  digitalWrite(LED_GREEN, LOW);
  digitalWrite(LED_RED, LOW);

  Serial.println("==================================================");
  Serial.println("   Running Embedded Self-Test Unit Harness...     ");
  Serial.println("==================================================");

  bool all_passed = true;

  if (test_zero_scale()) {
    Serial.println("[PASS] Test 1: Zero Scale (0 counts -> 0 mV)");
  } else {
    Serial.println("[FAIL] Test 1: Zero Scale Failed!");
    all_passed = false;
  }

  if (test_full_scale()) {
    Serial.println("[PASS] Test 2: Full Scale (4095 counts -> 3300 mV)");
  } else {
    Serial.println("[FAIL] Test 2: Full Scale Failed!");
    all_passed = false;
  }

  if (test_mid_scale()) {
    Serial.println("[PASS] Test 3: Mid Scale  (2047 counts -> 1649 mV)");
  } else {
    Serial.println("[FAIL] Test 3: Mid Scale Failed!");
    all_passed = false;
  }

  Serial.println("--------------------------------------------------");
  if (all_passed) {
    digitalWrite(LED_GREEN, HIGH);
    Serial.println("[ALL TESTS PASSED]: Hardware Green LED illuminated!");
  } else {
    digitalWrite(LED_RED, HIGH);
    Serial.println("[TEST FAILED]: Hardware Red LED illuminated!");
  }
}

void loop() {}

// Mini-Project 2: Bare-Metal MISRA Assertion Framework
// ============================================================================
#include <stdint.h>
#include <stdbool.h>

#define GPIOA_BASE  (0x50000000UL)
#define GPIOA_BSRR  (*(volatile uint32_t *)(GPIOA_BASE + 0x18UL))

#define ASSERT_EQUAL(actual, expected) do { \
    if ((actual) != (expected)) return false; \
} while(0)

bool run_boot_verification(void) {
    // Assert calibration calculations
    ASSERT_EQUAL(((uint32_t)0 * 3300UL) / 4095UL, 0);
    ASSERT_EQUAL(((uint32_t)4095 * 3300UL) / 4095UL, 3300);
    return true; // All assertions passed
}

void indicate_test_result(bool passed) {
    if (passed) {
        GPIOA_BSRR = (1UL << 6); // Green LED (PA6) ON
    } else {
        GPIOA_BSRR = (1UL << 7); // Red LED (PA7) ON
    }
}

9. Concept Check Practice Questions

Question 1: In-Circuit Debugging: SWD vs. JTAG

NoteClick to View Question & Options

Why is ARM Serial Wire Debug (SWD) the standard debug interface on modern 32-bit Cortex-M microcontrollers rather than traditional 5-wire JTAG?

Options:
- A) JTAG does not work with C programming
- B) SWD achieves full hardware debugging, flash programming, and CPU control using only 2 physical pins (SWCLK and SWDIO), saving valuable pins on compact chip packages
- C) SWD eliminates the need for a power supply
- D) JTAG can only be used on 8-bit processors

Tip✅ Correct Answer: B

Explanation:
Standard JTAG requires 4 or 5 dedicated pins (TDI, TDO, TCK, TMS, TRST). On small 20-pin or 32-pin microcontrollers, dedicating 5 pins to debugging severely limits the number of pins available for sensors and actuators. SWD provides the same debugging capabilities over just 2 pins.

Question 2: Profiling with ARM DWT Cycle Counter

NoteClick to View Question & Options

What is the primary advantage of using the ARM Cortex-M Data Watchpoint and Trace (DWT) cycle counter (DWT->CYCCNT) for execution profiling compared to inserting printf() statements?

Options:
- A) printf() increases the CPU clock speed
- B) DWT->CYCCNT measures execution time at single-clock-cycle precision with zero software overhead, avoiding the massive timing delays introduced by serial printf() calls
- C) DWT registers are stored in Flash memory
- D) printf() can only display negative numbers

Tip✅ Correct Answer: B

Explanation:
printf() involves formatting strings and waiting for bytes to shift out over a serial bus, adding milliseconds of delay and completely altering real-time software timing (the Heisenbug problem). The DWT cycle counter is a dedicated silicon hardware counter that reads in a single clock cycle with zero overhead.
